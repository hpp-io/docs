# Gas sponsorship

Every transaction on HPP costs gas in ETH. With sponsorship, your users never need ETH: HPP's
**paymaster** covers the gas for the operations your policy allows, and — if you choose — charges the
gas in **USDC.e** once the free ones are used up.

This is the same mechanism [HPP Smart Wallet](./wallet.mdx) uses for its "first operations free, then
USDC.e" model.

## Policies and anchors

Two IDs decide whether an operation is sponsored:

| | What it is | Who sets it |
| --- | --- | --- |
| **`policyId`** | Your app's rules: which fee mode, how much per month, per user, per operation, per day, and until when | HPP issues it to your app |
| **`anchorId`** | One **user** of your app, as your app identifies them (an account ID, not an address) | **Your backend** attaches it for the logged-in user |

Limits count per anchor, not per address — a user cannot get more free operations by creating more
addresses. Never let the end user type their own `anchorId`; your backend decides it after login.

```ts
const user = await createHppAccount({
  owner, chain, bundlerUrl,
  paymaster: { policyId: "<your policy>", anchorId: "<user id from your backend>" },
});
```

The paymaster shares the bundler endpoint (`/rpc`) and speaks the standard
[ERC-7677](https://eips.ethereum.org/EIPS/eip-7677) paymaster API, with `{ policyId, anchorId }` as the
context.

## Fee modes

A policy has one of three modes:

| Mode | Who pays the gas | What the user needs |
| --- | --- | --- |
| `sponsored` | HPP | Nothing |
| `token` | The user, in USDC.e, charged after the operation runs | A USDC.e balance |
| `sponsored_then_token` | HPP for the first *N* operations per user, then the user in USDC.e | USDC.e once the free ones are used |

The SDK switches automatically: the same `sendCalls` goes through the free paymaster while free
operations remain, and through the USDC.e paymaster afterwards. Each result tells you which:

```ts
const r = await user.sendCalls([...]);
r.fee;   // { mode: "sponsored", freeRemaining: 2 }
         // { mode: "token", symbol: "USDC.e", decimals: 6, maxToken, charged, … }   ← charged = actual USDC.e taken
```

### What a user pays in USDC.e

The charge is the operation's actual gas cost, converted at the current ETH/USD price plus 5%, with a
minimum of 0.001 USDC.e. HPP keeps the exchange rate in line with public market prices.

**Show the fee before the user signs.** `quoteFee` returns the most the operation can cost:

```ts
const q = await user.quoteFee(calls);
if (q.mode === "token") ui.show(`up to ${formatUnits(q.maxToken, q.decimals)} ${q.symbol} (actual cost is charged)`);
```

Users need no separate "approve" step. When an operation will be charged in USDC.e and the allowance is
not enough, `sendCalls` adds a small `approve` for the paymaster to that same operation — one signature
in total.

## Get access

<Tabs groupId="network">
<TabItem value="sepolia" label="HPP Sepolia" default>

A shared **sandbox policy** is available for development. Email [support@hpp.io](mailto:support@hpp.io)
with your GitHub ID and a one-line description of your app; you will get:

- `policyId`: `dev-sandbox`
- `anchorId`: `dev:<your-github-id>`

Sandbox operations are free (`sponsored`), with a small monthly and daily cap per anchor. Use the anchor
for your own testing; when you are ready to onboard real users, ask for a policy of your own.

</TabItem>
<TabItem value="mainnet" label="HPP Mainnet">

Mainnet sponsorship is set up per app — there is no self-serve dashboard yet. Email
[support@hpp.io](mailto:support@hpp.io) with:

- your app's name, website, and what users do with it;
- the fee mode you want (`sponsored`, `token`, or `sponsored_then_token` with how many free operations);
- the contracts your users will call;
- expected users and operations per month;
- how your backend identifies a user (this becomes the `anchorId`).

We agree on limits with you and issue a `policyId`.

Until then, your users can still use smart accounts on Mainnet and pay their own gas — leave out the
`paymaster` option.

</TabItem>
</Tabs>

## When a request is refused

If an operation does not fit the policy, the paymaster refuses it **before** anything is sent, so nobody
pays gas. The SDK throws with a JSON-RPC error whose `data.reason` says why, and retries the transient
ones (`free_exhausted`, `fee_quote_stale`, `fee_allowance_missing`) by itself. The most common:

| `reason` | Meaning |
| --- | --- |
| `fee_balance_insufficient` | Not enough USDC.e for the fee |
| `budget_exceeded` | A monthly, per-user, or daily limit is reached — by default the operation fails; your app can retry without the paymaster so the user pays their own gas |
| `would_revert` | The calls would fail on-chain |
| `policy_required` / `anchor_unknown` | Missing or unknown IDs |

The full list, with fixes: [Errors & troubleshooting](./errors.mdx#paymaster-policy).

Paymaster approvals are short-lived (5 minutes by default) and cover the operation exactly as it was
when approved: sign and send right away, and do not change any field afterwards.
